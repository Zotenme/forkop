# ARM64 core comparison, 2026-11-17

Native `linux/arm64` containers in OrbStack, Linux 7.2.12, Debian bookworm.
Each run had its own network namespace, `CAP_NET_ADMIN`, no published ports,
a 256 MiB memory limit and no swap. This is a compatibility/resource experiment,
not a router performance or throughput benchmark.

The representative profile was generated by this repository's generator and
modeled the supplied masked configuration: five VLESS outbounds, Reality/Vision,
uTLS Chrome, two selectors, source-aware DNS and six actual binary rule sets.
Those files were served locally by the harness. Keys and addresses were test
values; live public DNS behavior and the user's real proxy servers were not
tested. There were 20 local HTTP round trips through VLESS Reality/Vision.

## Measured router-profile results

All sizes below are MiB (1,048,576 bytes). Process memory is RSS, not virtual size.

| Metric | Tiny 1.14.4-r1 | Extended 1.14.3-extended-2.7.3 | Compressed, same extended release |
| --- | ---: | ---: | ---: |
| Download archive / package | 9.13 | 32.81 | 20.32 |
| Extracted executable | 24.88 | 95.38 | 20.32 |
| Idle main process RSS | 30.02 | 69.03 | 98.57 |
| Main process RSS after 20 requests | 35.53 | 75.55 | 104.00 |
| Additional `version` process, peak RSS | 16.81 | 57.07 | 91.21 |
| Additional `rule-set decompile`, peak RSS | 26.20 | 68.29 | 93.29 before SIGKILL |
| Decompile elapsed time | 0.03 s | 0.06 s | killed at 1.29 s |
| Reality/Vision round trips | 20/20 | 20/20 | 20/20 before decompile |
| Survived parallel decompile | yes | yes | no |

The helper's RSS is shown separately from the main process. Summing RSS can
double-count shared file pages. Peak RSS in the failed compressed run is only
what was recorded before it was killed, not the memory it would need to finish.
These are individual runs; timings are illustrative and are not router timings.

The compressed router-profile run recorded `memory.events: oom=3, oom_kill=2`.
The helper returned 137 and the daemon returned -9. Docker marked the container
`OOMKilled=true`. The main process and helper were both killed during the
parallel decompile phase. The 256 MiB budget also covered Python, OpenSSL,
container-charged filesystem pages and other harness costs; this is evidence
of the peak-memory mechanism, not an exact model of OpenWrt's available RAM.

Tiny also passed the same profile with a **128 MiB** container budget, no swap:
20/20 round trips, 28.86 MiB idle RSS, 33.84 MiB after traffic, 26.35 MiB peak
helper RSS, and zero OOM events. This does not guarantee stability on a 128 MiB
router with Wi-Fi, nftables and other services consuming its RAM.

Repository checks `tests/sing_box_runtime.sh`, `tests/dns_query_chain.sh` and
`tests/function_order.sh` also passed in `forkop-ci` on an isolated repository
copy. Benchmark Python syntax and `git diff --check` passed.

## Compatibility checks

All three binaries accepted generated configs in both existing stock-detection
mode and explicit extended-capabilities mode, as well as a separate XHTTP
configuration. XHTTP was checked for config acceptance only. Tiny's actual
Reality/Vision/uTLS handshakes succeeded. No generated config was silently
replaced by a hand-written minimal config for these checks.

The smoke runner adds a local VLESS inbound and a direct route for it after
generation, and points all VLESS outbounds to that peer. This runtime adaptation
is recorded in `runtime.json`; it does not change production source files.

## Integration follow-up

The subsequent application change adds tiny selection in the installer and LuCI,
variant-specific updates, capability detection and rollback checks. Its installer
was also exercised with the actual upstream ARM64 IPK in Docker, and the resulting
binary accepted the representative config. The experiment above was recorded
before that integration and measures the core itself.

Flash usage of an actual OpenWrt overlay, procd/nftables lifecycle, live DNS
failover, throughput and long-term stability still require router validation.
